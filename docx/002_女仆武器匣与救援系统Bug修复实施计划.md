## 2. 现有实现与数据流

### 2.1 女仆任务与临时战斗

`CommonEventHandler` 监听服务端 `MaidTickEvent`，调用 `RescueSessionManager.tick`。未处于救援会话时，管理器读取 `MaidRescueProfileData`，根据当前工作任务在 `TaskModeProfile` 中配置的禁止、独行或羁绊模式，检查女仆自身、主人附近的敌对生物及近期攻击者。触发后使用 `TaskSwitchService.prepareAndSwitch` 切换到 TLM 原生 `TaskAttack`，或在救援信号路径中切换到每个女仆配置的 `IAttackTask`。

会话状态保存在女仆的 TLM `TaskDataKey`：`MaidRescueSessionData` 记录原任务、战斗任务、原点、维度、Home Mode、日程、开始时间和安静计时。退出时先用 `SafeTeleportService` 返回记录原点，再恢复原任务和状态。当前实现没有主手换装步骤，因此铁镐等原主手会原样保留到攻击任务中。

### 2.2 女仆库存、主手与饰品栏

TLM `EntityMaid` 分别持有主手/副手包装器、普通背包 `maidInv`、装备栏以及 `BaubleItemHandler maidBauble`。饰品栏不是“物品实现 `IMaidBauble` 即可自动识别”，而是由 TLM `BaubleManager` 建立物品到饰品行为的注册映射；本附属已有 `@LittleMaidExtension` 的 `BeyondSpaceExtension`，最合适的扩展点是在其 `bindMaidBauble` 中注册新饰品。

武器匣应直接遍历 `maid.getMaidBauble()` 查找对应物品，并通过饰品槽内的 `ItemStack` NBT 保存内部物品。主手使用 `getMainHandItem`/`setItemSlot(MAINHAND, ...)` 操作。交换不经过普通背包，因此背包是否已满不会影响交换。

### 2.3 战斗女仆书

`SpacetimeRescueCharmItem.use` 当前不区分潜行，任何右键物品入口都会在客户端打开任务配置界面。右键女仆时，`interactLivingEntity` 将配置副本保存到女仆 `MaidRescueProfileData`；潜行右键女仆只清除单个女仆绑定。书本自身只保存任务模式配置，不保存反向的“已绑定女仆列表”，因此现有结构无法准确执行“清除这一本书的全部绑定”。

计划为书本增加稳定 `BookId` 和绑定女仆 UUID 列表，并在女仆绑定数据中增加可选 `SourceBookId`。新绑定可以精确区分不同书本；旧存档没有这些字段时安全读取为 `null`/空列表。旧版无法追溯具体是哪一本书，因此仅在旧书没有索引时使用所有者范围的兼容清理，并用待处理记录保证未加载女仆以后加载时也能清理。

### 2.4 女仆身份与救援信号

- 女仆实体稳定标识：`EntityMaid.getUUID()`。
- TLM `MaidInfo.entityId` 的构造来源也是 `EntityMaid.getUUID()`，NBT 键名为 `MaidId`，不是运行时整数 `Entity.getId()`。
- Owner 使用玩家 UUID；`MaidWorldData` 以 Owner UUID 分组保存 `MaidInfo`。
- `DistressSignalData` 当前把女仆 UUID 保存到物品 NBT 的 `Selections[].Maid`，类型与 `MaidInfo.entityId` 一致。
- 网络包使用 `FriendlyByteBuf.writeUUID/readUUID`，类型一致。

“小号记录 ID”实际就是 TLM `MaidInfo.entityId`：稳定 UUID、保存在主世界 `SavedData`、可跨重启持久化，可以作为未加载女仆名录来源和 fallback，但不能代替运行时实体解析。

关键问题是 TLM 的记录生命周期：`EntityMaid.onAddedToWorld` 会从 `MaidWorldData` 删除该女仆，`onRemovedFromWorld` 才重新加入。因此该数据本质上是“当前未加载女仆记录”。当前 `MaidRosterService.buildRoster` 只遍历该列表，所有女仆已加载时列表必然为空。这就是救援信号名录空白的主要根因。S2C 包会先携带完整列表再打开界面，客户端没有提前打开后不刷新的路径。

修复采用三源合并且按稳定 UUID 去重：

1. `MaidTickEvent` 观察到的已加载女仆轻量运行时索引；
2. TLM `MaidWorldData` 的未加载女仆记录；
3. 救援信号物品已有的选择记录作为兼容 fallback。

运行时索引只在女仆 Tick/加入世界时更新内存，不写 `SavedData`，打开 UI 时不全世界扫描实体；实际召回时仍按 UUID 在各维度用 `ServerLevel.getEntity(UUID)` 查找已加载实体。保存 UI 时，服务端重新验证所有权与允许的战斗任务，客户端不能直接写真实物品数据。

### 2.5 跟随与安全传送

TLM 原生 `MaidFollowOwnerTask` 在非 Home、可移动、主人有效且同维度时工作。它的远距离阈值取女仆 `restrictRadius + 2`，而 `restrictRadius` 来自 TLM `MaidNonHomeRange` 配置，并非本附属固定 12 格。配置较大时，女仆在超过 12 格后仍会写入到主人的步行目标。

TLM 已提供 `EntityMaid.teleportToOwner(owner)`：在主人周围随机尝试十次，检查 `MAID_AVOID_BLOCK`、路径类型（可行走/水）、实体碰撞，并清除导航和相关记忆。本轮直接复用它，不重新实现第二套传送算法。新增逻辑只在服务端、非救援会话、非 Home、女仆可移动、主人存活且同维度时检查 3D 平方距离；`> 12` 对应 `distanceToSqr > 144`，成功后重置 TLM 导航管理器。`<= 12` 完全保留原寻路。

## 3. Bug 根因结论

1. **武器不切换**：当前会话只保存和切换 `IMaidTask`，从未读取饰品栏或修改主手。
2. **远距离仍步行**：本附属没有固定 12 格的跟随传送检查；TLM 原生阈值依赖可配置的 `MaidNonHomeRange + 2`。
3. **战斗女仆书按键冲突**：`use` 无潜行和命中类型隔离，所有右键物品入口都打开配置界面；书本也没有反向绑定索引，无法实现一键清除本书全部绑定。
4. **救援信号名录为空**：名录只读取 TLM 的卸载女仆 `MaidWorldData`；已加载女仆会被 TLM 主动从该 SavedData 移除。保存包也用同一个不完整集合做所有权校验，导致已加载女仆配置被拒绝。

## 4. 「女仆的武器匣」设计

### 4.1 物品与饰品注册

- 新物品注册名：`maid_weapon_case`，显示名“女仆的武器匣”，最大堆叠 1。
- 类 `MaidWeaponCaseItem` 实现 TLM `IMaidBauble`。
- `BeyondSpaceExtension.bindMaidBauble` 把注册物品绑定到 TLM `BaubleManager`。
- 加入现有工具与实用物品创造模式页。
- 新增模型；本轮先复用 Minecraft 原版 bundle 纹理作为稳定占位，不生成无关二进制贴图。以后可以仅替换模型的 `layer0` 指向自定义 `textures/item/maid_weapon_case.png`。
- 不擅自新增祭坛或工作台配方；需求未指定材料。游戏内人工验证可用创造模式或 `/give` 获取。

### 4.2 单槽持久化

- 在武器匣 ItemStack 根 NBT 的专用键下保存完整 `ItemStack.serializeNBT()`。
- 读取使用 `ItemStack.of`，保留物品、数量、耐久、附魔、名称、Lore、ForgeCaps 和模组 NBT。
- 所有 getter 返回副本，setter 保存副本，避免共享可变引用。
- 拒绝把任何武器匣放入武器匣，避免递归/自包含；不建立剑/斧白名单。
- 实现容器销毁内容处理和存储状态 tooltip；饰品同步声明为需要客户端同步。

### 4.3 库存右键交互

复用 1.20.1 `BundleItem` 使用的标准 API：

- `overrideStackedOnOther`：光标拿起空武器匣，对有物品目标槽右键，服务端容器逻辑安全取出完整目标栈并写入匣内；对空槽右键则取出匣内物品到该槽。
- `overrideOtherStackedOnMe`：武器匣位于槽中，右键携带物品时收纳；空光标右键时把内部物品交给光标。
- 仅响应 `ClickAction.SECONDARY`，检查槽修改权限、武器匣数量、内部状态、目标有效性和禁止递归条件。
- 操作遵循 vanilla 容器的客户端预测、服务端校验与菜单同步模型，服务器状态是最终权威，不另发一套容易重复执行的自定义库存包。

### 4.4 自动交换状态机

新增 TLM `TaskDataKey`：`MaidWeaponSwapData`，持久化：

- `active`，旧数据默认 `false`；
- 武器匣饰品槽索引；
- 本次交换随机 UUID token；
- 交换后理论上仍应位于武器匣中的原主手完整快照。

进入战斗只调用一次 `WeaponCaseSwapService.beginSwap`：

1. 服务端确认状态未激活；
2. 定位已装备武器匣；
3. 确认内部栈有效且不是武器匣；
4. 复制内部物品与当前主手；
5. 给即将放入主手的副本加入本模组专用、随机的临时 token；
6. 直接执行主手与匣内物品交换，不经过背包；
7. 写入 active 状态。

token 用于区分“系统换入的这一栈”和玩家后来放入的同类物品，避免只比较 Item 或 Java 引用；正常恢复会删除 token，并在 tag 为空时恢复为无 tag 状态。武器在战斗中产生耐久或模组数据变化不会破坏身份判断，恢复后这些变化随完整 ItemStack 回到匣内。

恢复时同时满足以下条件才反向交换：

1. active 为真；
2. 原饰品槽仍是武器匣；
3. 当前主手仍带本次 token；
4. 武器匣内部仍与记录的原主手完整序列化快照一致。

任一条件不满足，都视为玩家主动修改：不把玩家当前主手塞进武器匣，不覆盖匣内新内容；若主手仍是本次武器则只移除内部 token，然后清 active。原工具已安全存在武器匣或已被玩家主动取走，不产生复制或吞物。

`beginSwap` 放在任务切换前，使需要检查主手的第三方攻击任务看到备用武器；如果任务切换失败，立即安全回滚。正常安静结束、超时结束、玩家手动改变任务、清除绑定等所有现有退出路径都先调用恢复，再清会话。active 防止 AI Tick 反复交换。

## 5. 战斗女仆书全部清除设计

- 新增 `CombatMaidBookData`，为书本保存 `BookId` 和已绑定女仆 UUID 列表。
- `MaidRescueProfileData.Data` 新增可选 `sourceBookId`；老存档缺失时为 `null`。
- 右键女仆绑定时给书分配 BookId、写女仆 UUID 并把 BookId 一并写到女仆数据。
- 潜行右键单个女仆仍保留，且从当前书的列表删除对应 UUID。
- `SpacetimeRescueCharmItem.use` 中：潜行且为空气入口时由服务端执行全部清理；非潜行仍打开任务配置。
- `useOn` 在潜行右键方块时消费但不清除；`interactLivingEntity` 在潜行命中实体时消费实体路径，确保不会落入空气清理。
- 新绑定按 BookId 精确匹配。旧书/旧女仆没有 BookId 时，只清理该所有者的 legacy 绑定，这是旧格式无法区分具体书本后的兼容策略。
- 新增主世界 `PendingBindingClearData` 保存未加载女仆的待清理 UUID、所有者和可选 BookId；女仆加载并 Tick 时验证 UUID、Owner、Binder 和 BookId 后清理并删除待处理项。只在新增/删除待处理项时标脏，不每 Tick 写盘。
- 提示使用本地化 key，不硬编码中文。

## 6. 救援信号名录修复设计

- `MaidRosterService.observe` 维护已加载女仆轻量索引；`CommonEventHandler` 在现有 Maid Tick 中调用，无全世界实体扫描、无持久化写入。
- `buildRoster` 合并运行时索引、`MaidWorldData` 的未加载记录和物品旧 selections，按女仆 UUID 去重。
- 所有可验证记录必须匹配玩家 Owner UUID；物品旧 selections 仅作为兼容显示，未知项显示稳定 UUID 占位，不宣称已加载。
- `findLoadedMaid` 继续在每个维度用 UUID 直接查询，不使用运行时 Entity ID。
- `SaveDistressRosterC2SPacket` 使用同一服务端已知所有权集合校验，并允许保留该信号中原已存在的兼容项，避免保存 GUI 时意外丢失老数据。
- S2C 数据结构和 UUID 编解码无需另建协议；若字段不变则保持网络协议版本 1。

## 7. 客户端与服务端职责

服务端负责：武器匣真实内容、主手交换、active 状态、书本绑定索引、女仆绑定/清理、待处理清理、名录来源与 Owner 校验、任务切换、救援召回和传送。

客户端负责：标准库存预测与显示、tooltip、任务配置 GUI、救援名录 GUI，以及发送已有保存请求。服务器在处理 C2S 时重新确认手中物品类型、Owner、UUID 与任务类型。武器交换只从服务端女仆 Tick/救援调用，不会双端各执行一次。

## 8. 边界情况

- 无武器匣、匣为空、匣内损坏数据或嵌套武器匣：不交换且不激活。
- 女仆多个武器匣：按饰品槽顺序选择第一个有效且非空的武器匣；状态记录槽位，恢复不会误用另一匣。
- 背包已满：交换完全不经过背包，不受影响。
- 原主手为空：允许把空栈放入武器匣，恢复后仍回到空主手。
- 玩家中途换主手：token 不匹配，不自动覆盖。
- 玩家中途修改/卸下武器匣：内部快照或槽位不匹配，不反向交换。
- 武器耐久、附魔、名称和模组 NBT变化：整栈移动并用 token 识别，变化保留。
- 切换攻击任务失败：回滚交换并清会话。
- 玩家主动切任务：检测到任务 UID 与会话战斗任务不同，先安全结束换装，再保留玩家选的新任务。
- 世界保存时会话仍 active：`TaskDataKey` 保存状态、token 和原主手快照；重载后可继续验证恢复。
- 老会话没有换装数据：active 默认 false，不进行错误恢复。
- 主人无效、死亡、旁观、跨维度或女仆 Home/不可移动：不执行 12 格跟随传送。
- 13 格但无安全落点：原生 `teleportToOwner` 返回 false，保持原位置，不强制 `setPos`。
- `MaidWorldData.getPlayerMaidInfos` 返回 null：按空列表处理，不抛空指针。
- 同一 UUID 同时出现在加载索引、卸载记录和信号旧数据：去重，优先采用已加载实体的最新名称和维度。

## 11. 静态验证矩阵

- 场景 1/2：begin 只在 inactive 时交换一次；finish 只在 active 且 token/槽位/快照匹配时恢复一次。
- 场景 3/4：无匣或空匣直接返回 false，不写 active。
- 场景 5：面包没有 token，恢复分支不把面包写入匣。
- 场景 6：使用 `serializeNBT`/`ItemStack.of` 与完整栈直接交换，不按 Item 重新构造。
- 场景 7：距离平方 100 不进入 `> 144` 分支。
- 场景 8：距离平方 169 进入原生安全传送尝试。
- 场景 9：调用 `EntityMaid.teleportToOwner`，不直接传送到主人坐标。
- 场景 10～12：`use`、`useOn`、`interactLivingEntity` 三入口分别处理空气、方块、实体；只有潜行空气执行全部清除。
- 场景 13：UI 数据源包含信号 NBT 与 `MaidWorldData`，不要求实体加载；已加载实体来自运行时观察索引。
- 场景 14/15：物品、SavedData、网络均使用 UUID；`MaidWorldData` 持久化 `MaidId`。
- 场景 16：确认“小号记录 ID”是 `maid.getUUID()`，作为未加载名录 fallback 使用，不作为运行时整数实体 ID。
